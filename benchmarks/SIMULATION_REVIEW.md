# Extensibility simulation review

Reviewed on 2026-09-25. Reproduce with `npm run benchmark:simulation`.

## Scope and method

The fixture contains 160 invented capabilities: 20 resource families in four domains,
each supporting get, list, create, update, delete, validate, publish and export.
`records` is deliberately a new domain. None is registered in the production
catalogue, and none calls Microsoft services.

The scripted client searches a natural-language task with a supplied domain,
selects the first candidate, describes that candidate, checks the task arguments
against the returned schema and executes through the normal projection/executor.
Expected capability IDs only score the result afterwards; they do not select it.
Arguments and domain are supplied by the scenario, not generated by a model.
This tests an agent-shaped protocol workflow, not an LLM's reasoning ability.

## Reviewed outputs

Both compact and dispatcher selected the correct top-ranked capability in all
eight scenarios. The lifecycle transcript showed:

| Task | Observed result |
| --- | --- |
| Create finance markings | Record in `draft` state |
| Verify finance markings | `valid: true`, record still draft |
| Publish finance markings | Record becomes `published` |
| Inspect finance markings | Reads the published state |
| Modify endpoint guardrails | Reads back the supplied `Reviewed` note |
| Find medical detectors | First page contains 25 records |
| Download legal schedules | Routes to the synthetic export handler; no real export is claimed |
| Delete finance markings | Record removed from fake state |

All 13 additional checks passed in each mode. Unknown and hidden capabilities
produced the same unavailable code, including hidden aliases. Direct execution
could not bypass read-only policy. A production-resource request was denied by
the argument-policy hook. Missing confirmation and unknown argument fields were
rejected before any handler ran. Restricted searches did not disclose write or
gated export schemas. A nonsense query returned no candidates. Pagination yielded
25/25/13 items, with 63 unique identities.

## Disclosure and scaling measurements

For these eight tasks, measuring serialized MCP result objects (both text and
structured representations, not model token counts):

| Mode | Lightweight search bytes | Selected describe bytes | Eager search bytes |
| --- | ---: | ---: | ---: |
| Compact | 43,862 | 13,852 | 68,716 |
| Dispatcher | 45,338 | 14,040 | 70,192 |

Search disclosed zero schemas per task; describe disclosed exactly one. Compared
with returning candidate schemas eagerly, combined search + describe responses
were about 16% smaller in compact and 15% smaller in dispatcher. This excludes
request envelopes and adds a round trip, so progressive disclosure is not a
universal latency win. `include_schemas:true` retains the lower-round-trip option.

Growing the fixture from 32 to 160 capabilities did not change tool counts:
compact exposed 10 (search + describe + four read/manage pairs), dispatcher 3.
At 160, their advertised schemas were 10,852 and 1,900 bytes respectively.
The production catalogue remains 27 capabilities, exposed as 8 compact or 3
dispatcher tools. Compact enums still grow with capability count; new domains can
add groups. Dispatcher is the constant-size option.

## Assessment and limits

- The extension path works for new domains and non-CRUD operations without MCP
  registration or executor changes. Explicit risk metadata makes `publish`
  destructive even though its name is not `delete`.
- Discovery, description and execution consistently respect capability policy.
  Resource-specific authorization remains an execution-time decision: being able
  to describe a schema is not permission to act on every object.
- The fixture uses short schemas and recognizable domain vocabulary. Eight
  scenarios are a regression set, not evidence of broad natural-language quality.
  Negation, ambiguity and implicit business intent remain the client's reasoning
  responsibility. Real-model evaluations should follow before claiming task-success
  improvements; no extra routing model is needed in production.
- The synthetic run is in-process. Separate real stdio and Functions HTTP tests
  exercise search/describe/execute and denied schema disclosure with the production
  server. No live Azure deployment or Microsoft tenant was tested.
- Long-running jobs are intentionally unsupported. Their future result/status/
  cancellation contract must be explicit; existing handlers cannot silently claim
  asynchronous work has completed.

Recommendation: retain compact for ordinary domain-oriented use, with dispatcher
available where minimum upfront schema disclosure matters. Expand this fixture
and its natural-language cases alongside each real capability family.
